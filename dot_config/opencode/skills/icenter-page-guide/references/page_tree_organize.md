# iCenter 页面目录树整理工作流

> **触发场景**：用户要求「整理 / 重组 / 归并某个父页面下的子页面目录结构」时加载本文件。
> 只是查询单个页面内容时**不需要**本文件（用 `get_page_detail_by_url` 即可）。

## 核心规则速查

| 环节 | 操作 | 关键点 |
|------|------|--------|
| 全量盘点 | `get_all_child_pages_by_url` | 2.0 descendant 通道，一次返回全量，**含根节点自身** |
| 设计结构 | （AskUserQuestion） | 目录结构主观，**先与用户确认再动手** |
| 建纯目录节点 | `create_page_by_url_with_content` | content **不能为空**，传 `<p></p>` |
| 改目录名 | `update_page_title_by_url` | 只改标题，页面 ID 与 URL **不变** |
| 归位 / 排序 | `move_page_by_url` | `pre_node_id` = "排到该节点之后"，**链式逐个调用**；**省略 pre 的落位不可控（可能最前/最后），要确定位置必须显式传前驱 id**（见第二节） |
| 核对 | `get_all_child_pages_by_url` | 看 `parentId` / `sortNo` / `parentPath`，**不要用 1.0 接口** |

---

## 一、整理流程（6 步）

### ① 全量盘点

```
get_all_child_pages_by_url(parent_url=父页面URL)
```

- 走 **2.0 原生 descendant 通道**，一次返回该父页面下**所有层级**的子节点，无分页
- 结果**含根节点自身**（`total_count` 把父页面也算一个）
- 每个节点带 `id` / `parentId` / `sortNo` / `parentPath` / `isLeaf` / `title`
- **据此可离线重建整棵树与同级顺序**：按 `parentId` 归组，组内按 `sortNo` 升序

### ② 设计目标结构并与用户确认

目录结构是主观的，**不要直接动手改树**。先给出「现状树 + 问题清单 + 目标树」，用
AskUserQuestion 让用户选（如：按主题重建 / 保守整理），并一并确认重复页、多版本页的处置策略。

### ③ 新建纯目录节点

```
create_page_by_url_with_content(
  parent_url=<父页面URL>,
  title="平台架构",
  content="<p></p>")            # ← 不能传空串
```

- `content=""` 会被拒：**"HTML内容不能为空"**（见错题本错误 24）
- 传 `<p></p>` 即可建成**无正文空容器**，与既有空容器形态一致
  （`query_page_chapter_tree_by_url` 返回 `blocks: []`）
- **先把旧容器改名，再新建同名容器**——否则同级重名会被静默追加时间戳（坑 5）

### ④ 改名

```
update_page_title_by_url(page_url=<页面URL>, title="技术方案")
```

- **只改标题，页面 ID 与 URL 不变**，对外链接不失效
- **空容器**可安全当纯目录改名；**有正文的页面**改名前要谨慎（它同时是一篇文档）
- 工作汇报类的个人前缀（如「张三00123456 - 」）属可选清理项，须在方案确认时一并说明

### ⑤ 归位与排序

```
move_page_by_url(
  page_url=<被移动页面URL>,
  target_parent_url=<目标父页面URL>,
  pre_node_id=<排到这个节点之后>)
```

- 移动**容器节点时其子孙随迁**，无需逐个移动子孙
- 排序算法见第二节
- 返回体带 `target_reached`（移动后回读父节点是否等于目标），**逐次校验**，
  不要等全部做完才发现错位

### ⑥ 核对

再用 `get_all_child_pages_by_url` 回读，逐层核对 `parentId` / `sortNo` / `parentPath`。

---

## 二、同级排序：链式插入（最关键）

### 语义

- `pre_node_id` = **"把被移动节点排到该节点之后"**，该节点必须是**目标父页面的子节点**
- 服务端排序算法：`newSortNo = (前驱 sortNo + 目标容器内下一个更大 sortNo) / 2`；容器内找不到更大的
  `sortNo` 时取 **`前驱 sortNo + 100`**
  （接口的 `moveType` 字段**被服务端完全忽略**，勿尝试用 `before` 等取值改变语义）
- **省略时客户端回落为 `target_node_id`（即目标父节点自身）**（实现：`"preNodeId": pre_node_id or target_node_id`）
  → 前驱变成**父节点**，落位由数值关系决定：`(父节点.sortNo + 容器内第一个子节点.sortNo) / 2`。
  **⚠️ 落位不可控，既可能最前也可能最后**：
  - 父 sortNo **小于**子节点（老页面常见，子节点经历了多轮排序、数值较大）→ 结果小于所有子节点 → **落在最前**
  - 父 sortNo **大于**子节点（新建容器常见，子节点从 100 起、父节点是较晚分配的大值）→ 结果大于所有子节点 → **落在最后**
  - 两种都只是同一公式的数值后果，**不要依赖"省略 pre = 追加到末尾"**（旧文档结论；2026-10-09 复核实为数值巧合）

**2026-10-09 实测（两处场景，全符合同一公式）：**

| 场景 | 调用 | 结果 sortNo | 落位 |
|------|------|------------|------|
| 老页面（父 1100，子 1850/…/2550） | `move(X, parent)`（省略 pre） | 1475 = (1100+1850)/2 | **最前** |
| 同上，再移一个 | `move(Y, parent)`（省略 pre） | 1287 = (1100+1475)/2 | **最前** |
| 新建容器（父 2650，子 100/200/300） | `move(Z, c)`（省略 pre） | 1375 = (2650+100)/2 | **最后**（大于 300） |
| 任意 | `move(Z, parent, pre=X[100])` | 150 = (100+200)/2 | 紧跟 X 之后 |
| 任意 | `move(W, parent, pre=<当前最后一个兄弟 2550>)` | 2650 = 2550+100 | **末尾**（真正的追加） |

> ⚠️ 两条推论：
> 1. **要精确落位（含"追加到末尾"），必须显式传目标前驱的 id**：末尾追加 = 传"当前最后一个兄弟节点"的 id。
> 2. **批量（同一批消息）移入同一父容器且都不传 pre 时**，各节点会算出**相同 sortNo**，
>    组内相对顺序不可控（实测呈倒序/乱序）。要定序，必须**逐个**用 `pre_node_id` 钉位。

### 排法

要把某父页面的子节点排成 `[c1, c2, ... cn]`：**按序逐个调用**——
c1 钉到它的目标前驱之后（"追加到末尾"就传移动前的最后一个兄弟；想排到最前则传…见下方写法），
c_i 传 `c_{i-1}` 的 ID。

原理：每一步插入都锚定在前一个节点之后，最终全局顺序恰为 `[c1..cn]`。

### ✅ 正确写法（链式、逐个）

```
# 目标：把 c1..c3 依次追加到容器【末尾】（先记下移动前的最后一个兄弟 last）
move(c1, parent, pre_node_id=last.id)
move(c2, parent, pre_node_id=c1.id)
move(c3, parent, pre_node_id=c2.id)
```

- **不要用"省略 pre"来充当某个位置**：省略 pre 的落位取决于父/子 sortNo 数值关系
  （可能最前、可能最后），不可控；任何确定落位都显式给 `pre_node_id`。
- 若 c1 与其它省略 pre 的节点同批下发，它们会拿到相同 `sortNo`、组内顺序不可控（见上方 ⚠️）。

### ❌ 错误写法（同一条链并行发出）

```
# 不要这样做：一次消息里并行发出同一条链的多个 move
move(c1, parent);  move(c2, parent, pre=c1);  move(c3, parent, pre=c2)
```

并行调用的**完成顺序不确定**，而链式插入的每一步都依赖前一步已落位 → 结果顺序不可控。

**可以并行的情况**：跨**不同父节点**的移动互不影响，可并行
（例如同时往 4 个不同容器各追加第一个元素，之后各链再分别串行推进）。

## 三、坑清单

| # | 坑 | 现象 | 处置 |
|---|----|------|------|
| 1 | **1.0 详情接口有读缓存**（历史结论；工具层已屏蔽） | `GET /zte-rd-icenter-contents/content/{id}` 按 content_id 缓存，页面移动后仍返回旧 `parentId` / `sortNo` / `isLeaf`（实测 ≥300 秒不更新）；cache-buster 查询参数与 `Cache-Control: no-cache` 均无效 | **目录字段一律以 2.0 原生接口为准**（`get_page_detail*` 已实现"正文取 1.0、目录字段用 2.0 覆盖"，从工具侧观察不到该缓存；2026-10-09 未直接复核 1.0 原始行为） |
| 2 | **1.0 子节点接口报错（2026-10-09 未再复现）** | 2026-09-29 曾实测 `get_child_pages` 直接报「服务器错误」；2026-10-09 在两个父页面上复测均**正常返回** | 盘点与核对**优先**用 `get_all_child_pages_by_url`（2.0 descendant，一次全量、含根节点自身）；1.0 接口若报错再降级处理 |
| 3 | **非法 ID 文案误导** | `pre_node_id` 传成标题 / 分组名等非 32 位十六进制 → 服务端只回「请求参数错误，请检查后重试」，与限流、故障无关 | 传 ID 前做 32 位十六进制预校验 |
| 4 | **目标不存在** | 目标父页面 ID 格式合法但不存在 → 「因页面目录发生变化，页面移动失败，请重新调整页面顺序」 | 先确认目标父页面存在 |
| 5 | **同级重名静默改名** | 标题被追加 5 位时间戳（epoch 后 5 位） | 返回体带 `title_conflict` / `requested_title` / `title_conflict_existing_id`；**判断成败不要只看 `success`** |
| 6 | **移动成环** | 不能移动到自身或自身子孙之下 | 设计目标结构时即避免 |

## 四、实战范例（2026-09-29）

把「智能体平台」父页面从 **15 个一级节点**重组为 **7 个主题域**：

| 动作 | 数量 | 说明 |
|------|------|------|
| 新建空容器（`<p></p>`） | 4 | 平台架构 / 用户交互 / WebSocket通信 / 聊天记录持久化 |
| 改名 | 5 | 4 个空容器改为目录名 + 工作汇报去工号前缀 |
| 移动 | 15 | 12 次归入容器 + 3 次一级节点重排 |

结果：节点总数 46 → 50（原 45 个后代 + 4 个新容器），**内容零改动、页面 ID 全不变**；
选定的策略是「按主题重建目录 + 重复页原样保留」。

## 五、收尾检查清单

```
节点总数核对：
  → 原节点数 + 新建数 == 回读的 total_count ？
容器内顺序核对：
  → 每个容器的子节点 sortNo 是否升序且符合设计顺序 ？
层级核对：
  → 逐节点看 parentPath，有无页面遗留在错误层级 ？
  → 预期的空容器是否都还在（有没有被静默改名成 xxx_12345）？
```
